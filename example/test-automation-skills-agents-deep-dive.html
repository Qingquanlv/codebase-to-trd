test-automation-skills-agents 深度解读

面向QA自动化工程师的 AI Agent 知识库——工具无关的测试智能中枢
这个项目是由哥伦比亚 SDET 工程师 Douglas Urrea Ocampo 构建的一套面向 QA 自动化工程师的 AI Agent 定义库，涵盖 13 个专业 Agent、10 个可复用 Skill 以及 6 条跨切面 Instruction。它不是一个可运行的软件，而是一个"QA 自动化大脑"——通过结构化的 Markdown + YAML Frontmatter，将测试领域知识编码为 AI 工具（GitHub Copilot、Claude、Cursor 等）可直接消费的提示词资产。读完本报告，你将深刻理解：这套知识库如何用"Test Orchestration Pattern"驱动多 Agent 协作，如何用"Test Constitution"保证跨 Agent 的质量一致性，以及如何用"渐进加载"控制 AI 上下文成本。

核心结论

  • 这是一个 纯文档型知识库，零代码、零构建系统——其价值在于将 QA 自动化经验封装为 AI 提示词资产，而非可执行软件。
  • Test Orchestration Pattern (TOP) 是核心架构：8步工作流（Initialize → Explore → Plan → Generate → Implement → Review → Refactor → Run），将复杂测试任务拆解为有序的 Agent 协作链。
  • Test Constitution（测试宪法） 是质量保障机制：6条 MUST DO + 5条 WON'T DO 规则，在 QA Orchestrator 中集中定义，强制下发给所有子 Agent，确保"DI via fixtures、Selector 优先级、禁用硬等待"等规则贯穿所有生成代码。
  • Skill 的 三级渐进加载 是极具工程智慧的设计：Level 1 仅暴露 name+description 用于发现，Level 2 加载完整 SKILL.md，Level 3 按需加载 references/scripts，有效控制 AI 上下文 Token 消耗。
  • Agent Handoff 机制 实现了有状态的多 Agent 工作流接力，Context Passing Template 确保每次 Agent 切换时关键信息（projectPath、featureName、previousOutput）不丢失。

1 摘要

1.1 项目背景

随着 GitHub Copilot、Claude Code、Cursor 等 AI 编程助手的普及，QA 工程师面临一个新问题：AI 工具功能强大，但不懂测试领域的"潜规则"——不知道该用 getByRole 而非 XPath，不知道不能用 waitForTimeout，不知道 POM 类该用 fixture 注入而非直接 new。每个工程师需要反复给 AI 讲解这些约束，耗时且难以在团队间统一。

这个项目的诞生背景是：把可重用的 QA 测试专业知识结构化，让 AI 助手"开箱即用"地成为一个懂测试的伙伴。通过将知识编码为 Agent 定义文件（.agent.md）、Instruction 规则（.instructions.md）和 Skill 手册（SKILL.md），团队可以一次编写、到处使用，无论用哪种 AI 工具，都能保持一致的测试自动化标准。

1.2 项目预期

1.2.1 预期一：标准化 QA 知识库

通过统一的 Markdown + YAML Frontmatter 格式，把 Playwright TypeScript、Selenium Java、无障碍测试（WCAG 2.1 AA）、ISTQB 手工测试等领域的最佳实践固化下来。任何新加入项目的工程师都能通过复制这套资产到自己的仓库，立即获得一个"懂行"的 AI 测试助手，而不需要手动编写大量提示词。

1.2.2 预期二：AI 驱动的端到端测试提效

基于 Test Orchestration Pattern（TOP）的 8步工作流，将"从零编写测试"这一耗时任务完全交给 AI Agent 链路处理：Planner 探索应用 → Generator 生成测试代码 → Healer 调试修复失败用例 → Refactor Specialist 提炼重构。工程师从"写代码"转向"审查和验收 AI 的输出"，目标是显著降低编写高质量自动化测试的时间成本。

1.2.3 预期三：工具无关的可移植性

同一套知识资产（Agent 定义、Skill 手册、Instruction 规则）能够适配 GitHub Copilot、Claude Code、Cursor、Windsurf、Gemini CLI 等主流 AI 工具。Copilot 通过 .github/agents/ 目录发现资产；Claude 通过 CLAUDE.md 加载上下文；Cursor 通过 rules 系统消费 instruction 内容。一次投入，多工具受益。

2 项目设计理念

2.1 Test Constitution（测试宪法）：规则内化而非外化

传统做法是把编码规范写进文档，靠人来记忆和执行，结果是"规范在 Wiki 里睡觉，代码里活跃着各种 XPath"。这个项目的做法是将规则直接嵌入 Agent 定义——每个 Agent 文件都包含 ## Constitution (from TOP) 章节，列出 MUST DO 和 WON'T DO。这些规则不是建议，是 Agent 在生成任何代码之前必须检查的硬性约束。

核心规则包括：fixture 依赖注入（禁止在 spec 中 new PageObject(page)）、Selector 优先级（getByRole > getByLabel > ... > CSS）、禁用硬等待（永不使用 waitForTimeout 或 Thread.sleep）。通过让 AI 在生成代码前"先读宪法"，把过去需要代码审查才能发现的问题前置到生成阶段。

2.2 关注点分离：Agents / Instructions / Skills 三层架构

项目将 AI 的行为能力分为三个正交维度：

  • Agents（谁）：定义身份、专业范围和工具访问权限。每个 Agent 是一个"有个性的专家"——Flaky Test Hunter 只做不稳定测试分析，不改应用代码；API Tester Specialist 只做接口测试，不做 UI 测试。最小权限原则贯穿始终。
  • Instructions（怎么做）：跨切面的操作规则，约束所有 Agent 的行为一致性。比如 playwright-typescript.instructions.md 规定了所有 Playwright 代码必须遵循的编码标准，无论是 Generator 还是 Healer 都必须遵守。
  • Skills（做什么）：可复用的任务手册，包含步骤、参考文档和脚本模板。Skills 是按需加载的——只有当用户的请求匹配到 skill description 时，AI 才会加载完整的 SKILL.md 内容。

2.3 渐进式知识加载：控制 Token 成本

每个 Skill 文件夹中的内容遵循三级加载策略，这是专门为 AI 上下文窗口限制设计的工程权衡：Level 1 只暴露 name + description 供 AI 决定是否相关；Level 2 加载完整 SKILL.md（核心工作流）；Level 3 只有当 AI 显式引用时才加载 references/、scripts/ 下的资源文件。这避免了"一次性将所有文档塞入 prompt 导致 Token 爆炸"的反模式。

2.4 工具无关设计：内容与平台解耦

项目坚持"内容与工具分离"——测试领域知识（Locator 策略、POM 模式、ISTQB 方法论）与特定 AI 工具的集成方式（Copilot 的 .github/ 路径、Claude 的 CLAUDE.md、Cursor 的 rules）完全解耦。核心知识只写一次，通过简单的文件复制或 Git submodule 同步到各工具的发现路径。这使得团队切换 AI 工具时，知识资产无需重写。

3 系统详细设计

3.2 关键模块实现细节

3.2.1 关键模块一：Test Orchestration Pattern（TOP）8步工作流

📁 instructions/orchestration-workflow.instructions.md 🏷️ 管道模式 + 责任链

TOP 定义了 AI 驱动测试自动化的标准工作流。它解决了一个核心问题：AI 在没有结构化约束时会直接"跳到写代码"，跳过探索应用、设计场景等关键前置步骤。TOP 强制要求"在未探索真实应用 DOM 之前，禁止写任何 Locator"（Step 2: Explore），这一规则直接预防了大量因 DOM 假设错误导致的脆弱测试。

每个步骤有明确的 State 机器（PENDING / RUNNING / SUCCESS / SKIPPED / FAILED），允许工作流在失败时精确回退（生成代码有问题 → 回到 Step 4，基础设施缺失 → 回到 Step 5），而不是全部从头来过。

3.2.2 关键模块二：QA Orchestrator Agent（测试宪法 + 路由表）

📁 agents/qa-orchestrator.agent.md 🏷️ Orchestrator 模式 + 策略模式

QA Orchestrator 是整个系统的大脑，承担两个核心职责：一是维护 Test Constitution（测试宪法）——集中定义所有子 Agent 必须遵守的质量规则；二是维护 Workflow Routing Table（工作流路由表）——根据任务类型决定调用哪条 Agent 链路。

Constitution 的设计非常有趣：它不是靠"继承"传递（AI 上下文不保证继续），而是靠"复制"传递——每个子 Agent 文件里都有 ## Constitution (from TOP) 段落，原文摘抄规则。这看起来有重复，但实际上是为了确保子 Agent 在单独被调用时（不经过 Orchestrator）也能自我约束。这是一种防御性设计：不依赖调用链的完整性，而是让每个节点自包含。

3.2.3 关键模块三：Skill 渐进加载系统

📁 skills/*/SKILL.md + references/ + scripts/ 🏷️ 懒加载 + 分层缓存

Skill 系统的三级渐进加载是本项目最具工程价值的设计之一，它直接回应了"AI 上下文窗口有限"这个现实约束。类比数据库索引：不是把整张表加载到内存，而是先查索引（Level 1: description），需要时再加载行数据（Level 2: SKILL.md），最后按需加载大字段（Level 3: references）。

description 字段的设计非常考究——它必须同时包含 WHAT（做什么）、WHEN（什么时候用）和 KEYWORDS（用户会输入的关键词）。以 qa-manual-istqb 为例，其 description 足足 200+ 字符，涵盖了所有可能触发词："test plans, test strategies, test conditions, test cases, bug reports, defect logs, regression suites, traceability matrices..."。这是一种 关键词密度优化——让 AI 在 Level 1 阶段就能精准匹配用户意图。

3.2.4 关键模块四：Flaky Test Hunter（根因分析驱动的修复）

📁 agents/flaky-test-hunter.agent.md 🏷️ 诊断驱动 + 防御性编程

Flaky Test Hunter 是整个 Agent 库中设计最精细的专业 Agent。它解决的问题是：不稳定测试是测试套件的慢性毒药，传统处理方式要么是盲目加 timeout，要么是 skip 掉了事。这个 Agent 强制要求先诊断根因再开药——在 Constitution 中明确写道"NEVER increase timeout thresholds as the primary fix — timeout increases hide root causes"（不稳定测试加 timeout 只是治标不治本）。

Agent 将不稳定原因分为四大类（Timing / State / Environment / Resource），并为每类提供具体的修复模式。验证标准也非常严格：fix 之后必须连续运行 10+ 次确认稳定，而不是"跑了一次过了就算"。这体现了一种"证据驱动"的工程文化，与一般的快速修复心态形成鲜明对比。

// 文件: agents/flaky-test-hunter.agent.md（常见不稳定模式示例代码）

// ❌ FLAKY: Race Condition — 点击后立即断言，未等待异步操作完成
test("creates user", async ({ page }) => {
  await page.click("#create-user");
  // 问题：API 响应可能比断言慢，竞态条件导致随机失败
  expect(await page.textContent("#user-count")).toBe("1");
});

// ✅ STABLE: 用语义化等待替代时序依赖
test("creates user", async ({ page }) => {
  await page.click("#create-user");
  // 等待 DOM 状态而非固定时间：data-count="1" 是 API 完成的信号
  await page.waitForSelector('#user-count[data-count="1"]');
  expect(await page.textContent("#user-count")).toBe("1");
});

// ❌ FLAKY: Shared State — 测试间数据污染
test("lists users", async ({ request }) => {
  const response = await request.get("/api/users");
  // 如果 "creates user" 先跑，user 数量会不一致
});

  const uniqueId = Date.now().toString();
  // 每次测试创建独立数据，不依赖执行顺序
  const response = await request.post("/api/users", {
    name: `John-${uniqueId}`, email: `john-${uniqueId}@test.com`,
  });
  expect(response.status()).toBe(201);
});

4 方案评价

4.1 优势分析

  • 知识密度极高的领域建模：将 ISTQB 方法论、Playwright 最佳实践、无障碍测试标准等多个专业领域的知识精准结构化，是一个真实 QA 专家经验的高质量编码。
  • Test Constitution 的防御性设计：规则在每个 Agent 中本地副本化，而非依赖调用链继承，防止了 AI 上下文断裂时质量规则丢失的问题。
  • Skill 渐进加载是真实的工程优化：直接解决 AI Token 成本问题，description 的关键词密度设计体现了对 AI 工作机制的深刻理解。
  • 工具无关设计：同一知识资产适配 5+ 种 AI 工具，投资回报率高，团队切换工具时无需重写。
  • 完整的 E2E 测试工作流覆盖：从手工测试计划（ISTQB）到自动化代码生成（Playwright/Selenium），再到 CI/CD 流水线配置，覆盖了测试工程的全生命周期。
  • Claude Code Plugin Marketplace 支持：提供了一键安装路径（/plugin install test-automation-skills-agents），大幅降低使用门槛。

4.2 局限分析

  • 无运行时验证机制：作为纯文档库，无法验证 AI 是否真正遵守了 Constitution 规则——规则是否被执行完全依赖于 AI 模型的理解能力，无法自动检测违规。
  • Handoff 仅限 VS Code 环境：Agent 之间的 Handoff 机制目前只在 VS Code + GitHub Copilot 中完整支持，Claude Code 和 Cursor 中需要手动触发 Agent 切换，自动化程度降低。
  • 缺少实际项目示例：没有配套的示例项目（如 demo-webapp + 对应的测试代码），使得新用户难以直观看到"用了这个库之后，AI 到底会生成什么样的代码"。
  • Agent 之间耦合依赖文档约定：Agent 之间的协作靠 Context Passing Template 中的字符串变量（${projectPath} 等）传递，没有类型系统保障，变量名拼写错误或遗漏会导致静默失败。
  • 维护成本：Constitution 多处副本同步：MUST DO / WON'T DO 规则在多个 Agent 文件中重复，当需要更新规则时，必须手动修改所有副本，存在遗漏风险。
