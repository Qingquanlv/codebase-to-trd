andrej-karpathy-skills 深度解读

一套让 LLM 编码助手更可预测的行为约束框架 · 163k ⭐
andrej-karpathy-skills 是一套提炼自 Andrej Karpathy 对 LLM 编码观察的行为约束指令集，将四条原则编码为纯 Markdown，以插件、规则文件、Agent Skill 多种格式分发。通过注入 LLM 上下文（全局或按项目）来约束其编码行为，使其在开始编码前思考、始终保持简洁、修改时精准克制、执行任务时绑定可验证目标。通过 Claude Code 插件市场一键安装，或复制单个 Markdown 文件到项目中即可使用。

核心结论

  • 本质是一份「提示词宪法」——不添加任何新功能，只约束 LLM 的决策过程，通过消除四类高频错误行为来提升编码质量。
  • 四条原则（编码前思考、简洁优先、精准修改、目标驱动执行）每条都对应一个具体的 LLM 反模式，且互相独立，可单独使用。
  • 同一份原则同时以 Claude Code Plugin、CLAUDE.md、Cursor Rule、Cursor Agent Skill 四种格式分发，采用哪种格式不影响约束效果，选择权留给用户。

1 摘要

1.1 项目背景

2024 年底，Andrej Karpathy 在 X（原 Twitter）发帖总结了他使用 AI 编码助手的核心痛点：模型会代用户做假设然后默默执行、倾向于把代码写得过度复杂、修复一个 bug 时会顺手"改进"不相关的代码、以及面对模糊任务时缺乏可自主循环完成的能力。

forrestchang（@jiayuan_jy）将这些观察提炼成四条原则，打包成单个 CLAUDE.md 文件发布到 GitHub。项目在数天内获得 163k Star，成为当时 GitHub 上增长最快的仓库之一。multica-ai fork 版本在原版基础上增加了 Claude Code 插件市场和 Cursor Agent Skill 支持，使分发路径从"复制文件"升级为"一行命令安装"。

1.2 能解决的问题

1.2.1「模型默默假设执行」——编码前显式声明假设

LLM 面对模糊请求时倾向于选择一种解读然后立即执行，不告知用户它做了哪些假设。Think Before Coding 原则要求 LLM 在开始写代码前，先列出前提假设、呈现多种解读方案、在存在更简单路径时主动说出来。用户得以在实现偏离方向之前进行纠正，而不是在收到一大段错误代码后再返工。

1.2.2「代码越写越复杂」——最小代码解决当前问题

LLM 倾向于添加"以防万一"的功能、为一次性代码引入策略模式、把 5 行能完成的事写成 50 行类层次结构。Simplicity First 原则用一个判断标准来约束：资深工程师会不会说"这太复杂了"？通过明确禁止推测性功能和不必要的抽象，将代码的认知负担保持在任务的最小边界内。

1.2.3「改一处顺便改其他」——只碰必须碰的代码

LLM 在修复 bug 时会顺手更改引号风格、添加类型注解、重构相邻函数，使 diff 充满噪音且难以 review。Surgical Changes 原则要求每一行修改都必须能直接追溯到用户的请求，对不相关的死代码只提及不删除，匹配现有代码风格而不是统一成自己的偏好。

1.2.4「目标模糊无法无人值守完成」——绑定可验证的成功标准

弱任务描述（"修一下认证系统"）需要 LLM 不断向用户要求澄清，或自行猜测完成范围；任何一种情况都会打断用户的工作流。Goal-Driven Execution 原则将指令式任务转化为可验证目标，例如"写出重现 bug 的测试，再让它通过"，给 LLM 足够的退出条件来独立循环完成任务，不需要人工持续在场。

2 项目设计理念

2.1 单文件内聚：原则即指令

整个项目最核心的产物是一个 66 行的 CLAUDE.md 文件。项目刻意不引入任何配置格式、工具链或运行时依赖——原则本身就是指令，LLM 读到即执行。这一决策使"安装"的成本降低到一次 curl，也使维护成本降至最低：改一处（CLAUDE.md），同步到其他格式文件即完成。

2.2 行为约束，不是功能增强

市面上大多数 AI 编码工具的竞争点在于"能做到什么"——更强的代码补全、更好的 RAG 索引、更大的上下文窗口。这个项目反其道而行，关注的是"什么不能做"：不能默默假设、不能过度抽象、不能修改不相关代码、不能在没有验证标准的情况下认为任务完成。约束 LLM 的边界比扩展其能力边界更容易量化效果（观察 diff 即可）。

2.3 跨工具标准化（竞品横向对比）

同一套原则通过四种格式在两个主流 LLM 编码工具中可用，而不是各自维护一套工具特定的指令。这种设计降低了用户的认知负担，也让原则本身的效果更易于跨工具比较。

工具/方法定位优势劣势
andrej-karpathy-skills 跨工具行为约束指令集 极简安装、跨工具通用、原则来自实践观察、可合并到已有指令 只约束行为不增加能力、需用户自行判断何时生效、原则固定无法自适应
GitHub Copilot Instructions 项目级自定义指令（.github/copilot-instructions.md） 原生集成 VS Code/GitHub、团队共享方便 仅限 Copilot、无法跨工具使用、社区规则库较少
Cursor Rules (.cursorrules) 项目级或全局 Cursor 行为规则 灵活度高、支持 glob 匹配不同文件类型、社区规则库丰富 仅限 Cursor、格式与 Claude Code 不兼容、需自己提炼原则
自定义 System Prompt 直接向 LLM 注入全局指令 最灵活、不依赖任何工具 需手动维护、无版本管理、无法在团队间共享

andrej-karpathy-skills 在"低安装成本"和"跨工具通用"这两个维度上胜出；在"自适应调整"和"工具深度集成"上落后于工具原生方案。最适合的用户是同时使用 Claude Code 和 Cursor、希望在两者之间保持一致约束的开发者。

2.4 当前适合解决什么问题

✅ 适合的场景

  • 新功能开发（需要 LLM 在动手前先澄清边界）
  • 对已有代码库做局部修改（防止 diff 污染）
  • 需要无人值守长任务（绑定验证标准后 LLM 可自主循环）
  • 团队希望对 AI 编码行为建立共识规范
  • 同时使用 Claude Code 和 Cursor 的混合工作流

⚠️ 不太适合的场景

  • 一次性简单任务（"帮我改个变量名"不需要完整的 Think Before Coding 流程）
  • 纯探索性原型（要求快速迭代，过度谨慎会拖慢节奏）
  • 需要动态调整约束的场景（原则是静态的，无法根据任务类型自动松紧）
  • 期望 LLM 主动生成更多功能的场景（本项目的取向是"约束"而非"激发"）

3.3 状态存储载体

这是一个纯 Markdown 框架，没有运行时数据库。"状态"存在于以下三层：

层次载体持久性职责与真相来源
源码层 Git 仓库 + CLAUDE.md 永久 原则内容的唯一真相来源。所有分发格式必须与此同步
安装层 Claude Code 插件目录 / 项目 .cursor/rules/ / ~/.cursor/skills/ 持久（直到卸载） 原则在特定工具环境的本地副本，用户无需手动维护
会话层 LLM 上下文窗口（Context Window） 临时（会话结束后消失） 原则在 AI 编码会话中的运行时实例；alwaysApply: true 确保每次会话都重新注入

3.4 常见误解

  1. 误解：这是一个代码生成工具或 AI 能力增强工具。 — 实际上它只是一份注入 LLM 上下文的行为约束文本，不给 LLM 增加任何新能力，只限制它的某些行为倾向。
  2. 误解：安装后所有任务都会变慢，因为 LLM 要先"想"。 — 原则末尾明确说明偏向谨慎而非速度，对琐碎任务（简单拼写错误修复）用户应自行判断是否需要完整流程。
  3. 误解：四种分发格式效果不同，应该选"最强的"那种。 — 四种格式载体不同，激活时机不同，但注入的原则内容完全相同，效果取决于 LLM 是否读到，而不是格式本身。
  4. 误解：Cursor Rule（alwaysApply）比 Agent Skill 更强，应优先选用。 — alwaysApply 意味着每个任务都带着这套约束，包括不需要它的简单任务；Agent Skill 是按需加载，适合不想让规则干扰所有对话的用户。二者是"总是生效"对"按需调用"的取舍，不存在孰优孰劣。
  5. 误解：项目内容固定，无法扩展。 — README 明确说明这套原则被设计为"可合并"的：用户可以把它 append 到已有 CLAUDE.md，再添加项目特定章节，如"使用 TypeScript 严格模式"。

4 项目使用方式

4.1 从需求到交付的一次完整过程

以一个真实场景为例：开发者向 Claude Code 提出"帮我给用户上传接口加速率限制"，希望 LLM 能在不引入过度复杂性的前提下完成任务。

① 原则注入上下文
Claude Code 启动时自动读取项目中的 CLAUDE.md（或全局插件版本），将四条原则注入 LLM 的 system prompt 上下文。此步骤对用户透明。
② LLM 触发 Think Before Coding
收到"加速率限制"请求后，LLM 不立即开始写代码，而是先声明假设：「速率限制的粒度是按 IP、按用户还是按 API Key？限额是多少？后端是单机还是多实例？超限返回 429 还是排队？」然后等待用户确认。
③ 用户澄清 → LLM 制定计划
用户确认「按 IP，10 次/分钟，单机部署，429 响应」后，LLM 提出分步计划：
1. 添加 in-memory 计数器 → verify: 测试 11 次请求，第 11 次收到 429
2. 提取为中间件 → verify: 现有测试通过。这一步体现了 Goal-Driven Execution 原则。
④ LLM 执行 step 1 并验证
LLM 写出最小实现：一个 Map 存储 IP 计数、一段 middleware 逻辑、一个测试文件。不添加 Redis 后端（未被要求）、不添加配置文件（未被要求），体现 Simplicity First 原则。运行测试，验证通过。
⑤ LLM 执行 step 2，Surgical Changes
提取为 middleware 时，LLM 只修改相关的路由注册代码，不更改其他路由的签名、不添加类型注解（原有代码没有）、不改变引号风格。diff 仅包含与任务直接相关的行。
⑥ 计划完成，LLM 报告结果
两步均通过验证，LLM 报告：「速率限制已添加，两个测试均通过，未修改其他代码。如需 Redis 后端支持多实例，可在之后单独提出。」用户得到一个干净的、最小的实现。

5.3 关键模块实现细节

5.3.1 Think Before Coding 原则

📁 CLAUDE.md · ## 1. Think Before Coding 🏷️ 防御性决策 ⏱️ 每次收到用户请求时触发

要解决的问题：LLM 的默认行为是在面对歧义时选择一种解读然后立即执行。这不是因为模型"懒"，而是因为"回答"比"澄清"更符合训练数据中的对话模式。当需求模糊（"优化搜索"、"重构这段代码"）时，这种默认行为会导致大量无效工作：用户拿到一个完全方向错误的实现，然后不得不从零开始解释真实需求。

解决方案：原则通过四条具体指令改变这一默认行为：显式声明假设（而非隐式选择）、呈现多种解读（而非沉默选择一种）、主动提出更简单路径（而非总是服从）、遇到困惑时停下来命名不清楚的是什么（而非猜测继续）。关键是"停下来"的阈值被明确降低了——LLM 被授权打断对话去澄清，而不是必须给出一个答案。

sequenceDiagram participant U as 用户 participant LLM as LLM（受原则约束） participant Code as 代码库 U->>LLM: "把搜索做快一点" Note over LLM: Think Before Coding 触发 LLM-->>U: 呈现3种解读：
1.响应时间(< 100ms)
2.并发吞吐量
3.感知速度(UX) LLM-->>U: 声明假设：当前搜索约 500ms，主要是数据库查询 U->>LLM: 选择方向1，目标 100ms 以内 LLM->>Code: 精准实现：添加索引 + 缓存高频查询 Code-->>LLM: 实现完成 LLM-->>U: 报告：P99 降至 85ms，diff 仅含索引和缓存两处

5.3.2 Goal-Driven Execution 原则

📁 CLAUDE.md · ## 4. Goal-Driven Execution 🏷️ 验证驱动循环 ⏱️ 多步任务开始时 / 接收模糊任务描述时触发

要解决的问题：LLM 面对"修复认证系统"这类任务时，没有明确的"完成"定义，既可能做得太少（只改了一个小 bug）也可能做得太多（重写整个认证模块）。更严重的是，当 LLM 无法自主判断完成标准时，需要不断打断用户确认，破坏工作流的专注度。Karpathy 指出 LLM 擅长"循环到达成目标"，但前提是目标必须是可检测的。

解决方案：原则要求将每个任务转化为"写出能验证的测试，然后让它通过"的结构。关键机制是"验证步骤必须先于实现步骤出现"——在多步计划中，每个步骤形如 [动作] → verify: [检查]。这为 LLM 提供了一个无需人工确认就能退出循环的条件，使无人值守的长任务成为可能。

5.3.3 Claude Code Plugin 分发机制

📁 .claude-plugin/plugin.json + marketplace.json 🏷️ 两阶段安装（市场注册 → 插件安装） ⏱️ 用户执行 /plugin 命令时触发

要解决的问题：原版项目的唯一安装方式是"手动复制 CLAUDE.md 到项目目录"——这意味着每个新项目都要重复操作，且原则更新时所有项目的副本都要手动同步。multica-ai fork 增加了 Claude Code 插件市场支持，目标是让原则像 npm 包一样：安装一次全局生效，更新时统一维护。

解决方案：两个 JSON 文件构成两阶段安装流程：marketplace.json 描述"这个仓库是一个插件市场"（包含 plugins 数组和插件元数据），plugin.json 描述"这个插件包含哪些 Skill"（通过 skills[] 数组指向 SKILL.md 路径）。用户先用 /plugin marketplace add 注册市场源，再用 /plugin install 安装具体插件；Claude Code 读取 plugin.json 的 skills[] 路径，将 SKILL.md 内容加载为全局可用技能。

5.3.4 Cursor Rule（alwaysApply）激活机制

📁 .cursor/rules/karpathy-guidelines.mdc 🏷️ 声明式持续注入 ⏱️ Cursor 打开任意文件 / 创建会话时自动触发

要解决的问题：Claude Code 的 CLAUDE.md 在项目目录级别生效，开发者如果只使用 Cursor，需要一种等价但 Cursor 原生的方式来持续注入原则。更重要的是，手动把原则粘贴到每个新对话的 prompt 里既繁琐又容易遗忘。

解决方案：Cursor Rule 的 frontmatter 字段 alwaysApply: true 是关键设计：它告诉 Cursor 无论当前打开的是哪个文件、发起的是什么类型的对话，都将这条规则注入到 LLM 上下文。这意味着开发者无需"记住"激活原则这件事——只要规则文件存在于 .cursor/rules/，它就总是生效。规则正文与 CLAUDE.md 内容完全相同，维护者手动保持两者同步。

6 方案评价

6.1 优势分析

  • 安装成本接近零：Claude Code 两条命令、Cursor 复制一个文件、通用场景 curl 一行，无需配置任何工具链
  • 可验证的效果指标：是否生效不需要主观判断，直接看 diff —— 如果 diff 只包含请求相关的行，原则在起作用
  • 跨工具通用：同一套原则同时覆盖 Claude Code 和 Cursor，用户不需要为每个工具重新学一套规范
  • 可合并、可扩展：append 到已有指令文件，再加上项目特定章节，形成"基础层 + 项目层"的双层约束
  • 原则互相独立：四条原则各自解决独立问题，可以单独使用某一条而不影响其他
  • 来源权威：原则提炼自 Karpathy 的实际使用观察，不是理论推导，具有较高的实践可信度

6.2 局限分析

  • 静态规则，无法自适应：原则无法根据任务类型动态调整松紧，简单任务和复杂任务承受同等约束力
  • 无更新通知机制：安装后如果 upstream 更新原则，用户不会收到通知，需要手动同步多个分发格式文件
  • 效果依赖 LLM 遵守：原则是"软约束"——LLM 可能在某些情况下忽略，尤其是在非常长的上下文中原则可能被推出注意力窗口
  • 四种格式需手动同步：CLAUDE.md、.mdc、SKILL.md 内容相同但独立存储，维护者改动时需要手动同步三个文件
  • Goal-Driven 依赖测试基础设施：对没有测试的项目，验证原则的价值大打折扣；为遗留项目引入测试本身就是一个独立任务
  • 无量化评估工具：项目提供的"如何判断是否在起作用"的指标（diff 是否干净）是定性的，没有提供自动化评估工具
