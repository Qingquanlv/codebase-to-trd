Sharingan（写轮眼）深度解读

基于 Go 源码级 Hook 的生产流量录制与回放系统
Sharingan 是滴滴开源的一套流量录制回放工具，其核心思路是"录制线上真实流量，线下无依赖还原"。 它通过修改 Go 源码暴露 Hook 接口，在 goroutine 粒度精确捕获每一次入站/出站网络调用，形成完整的请求会话； 回放时利用 Monkey Patching 在二进制层拦截所有外部调用并由 Mock Server 返回录制的数据，使被测服务完全感知不到外部依赖的存在。 读完本文，你将深刻理解"生产流量如何在不改业务代码的前提下被完整镜像"，以及 goroutine-local storage、chunk 评分匹配等几个精妙的工程设计。

核心结论

  • Hook 层依赖定制版 Go 运行时，通过在 Accept/Connect/Send/Recv/Close 五个系统调用点插入回调，以零业务代码改动实现完整流量镜像。
  • 每个 goroutine 对应一个 Thread 对象，以 goroutine ID 为键维护独立 Session，天然支持并发录制而无需加锁。
  • 回放侧利用 gomonkey 在内存中直接替换函数机器码（JMP 指令），将所有 syscall.Connect、net.TCPConn.Read/Write 劫持到 Mock Server，业务代码无感知。
  • 流量匹配核心是"分块评分"算法：将请求切分为 16 字节 chunk，在录制的 Actions 中逐 chunk 计分，解决了 HTTP 参数乱序、协议二进制化等匹配难题。
  • time.Now() 也被 Monkey Patch 为返回录制时的时间戳，从根本上消除了时间因素（如签名、TTL）对回放结果的干扰。

1 摘要

1.1 项目背景

随着微服务架构的普及，服务依赖链路日趋复杂——一个请求可能串联十几个下游服务（MySQL、Redis、HTTP API、Thrift RPC 等）。 这给测试带来了两大痛点：其一，线下难以构造覆盖所有边界条件的测试数据；其二，测试环境中下游服务的不稳定性会导致大量误报，维护成本极高。

Sharingan 的目标是：录制线上真实请求流量（含所有下游调用），在线下进行回放验证，从而同时解决"测试数据构造难"和"下游依赖不稳定"两个问题。 项目名称取自《火影忍者》中的写轮眼——既能复制（录制），又能使用幻术（Mock），与项目能力高度契合。

1.2 项目预期

1.2.1 预期一：复制能力（并发录制）

在生产环境以极低的性能损耗录制真实流量，包括服务收到的所有入站请求和对应的所有出站下游调用。 录制结果以 Session 为单位持久化，每个 Session 完整保存一次请求的"上下文快照"：入站请求体、每个下游调用的请求与响应、最终返回给客户端的响应。 相比 tcpdump/goreplay 方案，Sharingan 能将出站调用与入站请求精确绑定，回放时不再依赖真实的下游服务。

1.2.2 预期二：幻术能力（无依赖回放）

回放时，被测服务发出的所有下游调用被 Mock Server（replayer-agent）拦截，Mock Server 根据录制的 Session 匹配并返回当时的下游响应。 被测服务完全感知不到外部依赖的切换，最终对比其回放响应与录制时的在线响应，从而验证重构或功能变更是否引入回归。

1.2.3 预期三：低侵入性

录制侧通过修改 Go 源码（而非业务代码）暴露 Hook 接口，业务代码只需在编译时指定 build tag（-tags="recorder"）即可接入录制，无需修改任何业务逻辑。 回放侧同理，只需在编译时加 -tags="replayer"，框架无关，支持 HTTP、gRPC、Thrift 等主流协议。

2 项目设计理念

2.1 接口与实现分离（Build Tag 热切换）

录制和回放功能通过 Go 的 build tag 机制实现"零成本切换"。核心接口文件（如 recorder/koala/hook/tag_with_recorder.go 和 tag_without_recorder.go）提供了同名函数的两套实现： 带 recorder tag 时编译真实 Hook 逻辑，不带 tag 时编译空函数。这样同一份业务代码可以在开发/测试/生产三种模式下编译，无需 if/else 或配置开关污染业务逻辑。

这种模式也让整个 Hook 层对 Go 运行时的侵入性降到最低——Hook 接口固定，具体实现可随 Go 版本更新而独立演进，项目 README 明确声明"所有改动通过官方测试用例"。

2.2 进程隔离代理（Agent 模式）

录制和回放的控制逻辑（流量存储、比例控制、Mock Server、覆盖率统计）均运行在独立的 agent 进程中（recorder-agent 和 replayer-agent）， 通过 TCP/Unix Socket 与被测服务通信。这种设计的好处是：agent 崩溃不影响被测服务；agent 可以独立部署和升级； 多个被测服务实例可共用一个 replayer-agent，降低运维成本。

2.3 二进制插桩（Monkey Patching）

回放侧选择了最激进但也最彻底的方式——在进程内存中直接修改目标函数的机器码，写入 JMP 跳转指令，将调用重定向到替换函数（gomonkey 库实现）。 这意味着即使是第三方库（如 MySQL driver）发起的 TCP 连接，也会被无声地重定向到 Mock Server， 而无需对这些库做任何修改。代价是需要关闭编译器内联优化（-gcflags="all=-N -l"）。

2.4 并发透明（Goroutine-Local Session）

Go 没有原生的 thread-local storage，但 Sharingan 通过读取 goroutine 的内部 ID（利用修改后的 Go 运行时暴露的接口）作为 key， 在全局的 map[ThreadID]*Thread 中维护每个 goroutine 的独立 Session。 这样并发处理的多个请求各自拥有独立的录制状态，Session 的构建完全无锁，高并发下性能损耗极低。

录制阶段：业务服务以 recorder build tag 编译后，koala 录制器在每个 goroutine 的 Accept/Connect/Send/Recv 事件上回调， 将网络数据汇聚到该 goroutine 对应的 Session 对象，goroutine 退出时异步将 Session 发送给 recorder-agent 持久化。

3.2 关键模块实现细节

3.2.1 关键模块一：Hook 机制（录制入口）

📁 recorder/koala/hook/hook.go 🏷️ 观察者模式 + Build Tag

要解决的问题：如何在不修改业务代码的情况下，拦截所有网络 I/O？

方案选择：修改 Go 源码，在底层 net 包的 Accept、Connect、Write、Read、Close 函数中加入回调点， 通过接口注册（RegisterOnAccept、RegisterOnSend 等）将事件分发给 koala。 相比于 eBPF（需要 root 权限，不支持内容修改）或应用层 middleware（需要改业务代码），这种方式最彻底也最透明。

核心逻辑：Hook 注册发生在进程启动时，Start() 函数一次性绑定五个系统调用的回调。 每个回调首先通过 GetCurrentGoRoutineID() 获取当前 goroutine ID，然后在全局 Thread Map 中找到（或创建）对应的 Thread， 再将网络事件分发给 Thread 上的 Session 对象。

// 文件: recorder/koala/hook/hook.go (line 15-42)
// Start 在进程启动时一次性注册所有网络事件的 Hook
func Start() {
    setupAcceptHook()    // 监听新连接（入站）
    setupConnectHook()   // 监听下游连接（出站）
    setupSendHook()      // 监听数据发送
    setupRecvHook()      // 监听数据接收
    setupCloseHook()     // 监听连接关闭
    setupGoRoutineExitHook() // goroutine 退出时触发 Session 落盘
}

func setupAcceptHook() {
    RegisterOnAccept(func(serverSocketFD int, clientSocketFD int, sa syscall.Sockaddr) {
        // 获取当前 goroutine ID，作为 Thread 的唯一标识
        gid := sut.ThreadID(GetCurrentGoRoutineID())
        origAddr := sockaddrToTCP(sa)
        // 全局 socket 表中登记此 FD（inbound 标志）
        sut.AddGlobalSock(sut.SocketFD(clientSocketFD), origAddr, true)
        // 在该 goroutine 的 Session 上记录 Accept 事件
        sut.OperateThreadOnRecordingSession(gid, func(thread *sut.Thread) {
            thread.OnAccept(sut.SocketFD(serverSocketFD), sut.SocketFD(clientSocketFD), origAddr)
        })
    })
}

3.2.2 关键模块二：Session 状态机（录制数据结构）

📁 recorder/koala/recording/session.go 🏷️ 状态机 + Builder 模式

要解决的问题：如何将一个 goroutine 处理期间的所有网络 I/O（可能涉及多个不同下游）正确地组织成一个可回放的"快照"？

核心数据结构：Session 内部维护一个 Actions []Action 列表，按时间顺序记录所有事件： CallFromInbound（入站请求）、多个 CallOutbound（每个下游调用的请求+响应）、ReturnInbound（最终返回）。 currentCallOutbound 游标追踪当前正在进行的出站调用，当 peer 地址或 socketFD 变化时自动新建 OutboundAction， 从而正确处理连接池复用场景。

设计亮点：addAction 内置过滤逻辑——只有在收到入站请求之后（HasRequest()==true）才开始记录 Action， 这消除了连接建立阶段的噪音数据，同时通过 ShouldRecordAction 钩子支持用户自定义过滤规则（如忽略心跳包）。

// 文件: recorder/koala/recording/session.go (line 122-138)
// SendToOutbound 处理出站请求，自动管理 CallOutbound 对象的生命周期
func (session *Session) SendToOutbound(ctx context.Context, span []byte, peer net.TCPAddr, local *net.TCPAddr, socketFD int) {
    if session == nil { return }

    // 以下三个条件任一满足，说明这是新的下游调用，需要创建新的 CallOutbound
    if (session.currentCallOutbound == nil) ||
        (session.currentCallOutbound.Peer.String() != peer.String()) || // peer 地址变化
        (session.currentCallOutbound.SocketFD != socketFD) ||           // socketFD 复用
        (len(session.currentCallOutbound.Response) > 0) {               // 上一次调用已有响应（新的一轮）
        session.newCallOutbound(peer, local, socketFD)
    } else if session.currentCallOutbound != nil && session.currentCallOutbound.ResponseTime > 0 {
        // 上一次调用因超时等原因返回了错误响应，开启新调用
        session.newCallOutbound(peer, local, socketFD)
    }

    session.currentCallOutbound.Request = append(session.currentCallOutbound.Request, span...)
}

3.2.3 关键模块三：回放核心（Monkey Patching + 连接重定向）

📁 replayer/fastmock/syscall.go 🏷️ Monkey Patching + 代理模式

要解决的问题：如何在不修改业务代码和第三方库的情况下，将所有出站连接重定向到 Mock Server？

方案对比：iptables 重定向（噪音大，影响系统全局）、动态链接库 hook（Go 是静态编译，不适用）、 修改 Go 源码（录制侧已用，回放侧可用同样思路但成本高）。最终选择 Monkey Patching（gomonkey）： 在运行时将目标函数的前几字节改写为 JMP 指令，跳转到替换函数，无需改源码也无需重链接。

三个关键 Patch： (1) syscall.Connect：将真实目标地址保存到 globalSockets，然后将 sa 替换为 Mock Server 地址后调用原始 Connect； (2) net.TCPConn.Read：对入站连接，解析并剥离 Sharingan 注入的 traceID/时间戳 Header，在 Thread Map 中登记映射关系； (3) net.TCPConn.Write：对出站连接，在数据头部注入 /*{"rid":"traceID","addr":"realAddr"}*/ 前缀， Mock Server 通过这个前缀识别请求归属的 Session 并查找录制的响应。

// mock syscall.Connect：将出站连接悄悄重定向到 Mock Server
func mockTCPConnConnect() {
    monkey.MockGlobalFunc(syscall.Connect, func(fd int, sa syscall.Sockaddr) (err error) {
        // 忽略 UDP socket
        sockType, _ := syscall.GetsockoptInt(fd, syscall.SOL_SOCKET, syscall.SO_TYPE)
        if sockType == syscall.SOCK_DGRAM {
            return internal.SyscallConnect(fd, sa)
        }
        // 未配置 Mock Server 时走真实连接
        if mockSaAddr == [4]byte{} || mockSaPort == 0 {
            return internal.SyscallConnect(fd, sa)
        }
        // 保存真实目标地址到全局 socket 表
        rsa := sa.(*syscall.SockaddrInet4)
        addr := net.TCPAddr{IP: rsa.Addr[:], Port: rsa.Port}
        globalSockets.Set(fd, addr.String(), internal.TimeNow())

        // 把连接目标替换为 Mock Server 地址
        msa := &syscall.SockaddrInet4{Addr: mockSaAddr, Port: mockSaPort}
        err = internal.SyscallConnect(fd, msa)

        // 100ms 后若没有 Write，主动发送 MySQL Greeting 特征前缀（处理 MySQL 握手）
        go func() {
            time.Sleep(time.Millisecond * 100)
            if socket := globalSockets.Get(fd); socket != nil {
                if accessTime == socket.lastAccessedAt {
                    prefix := fmt.Sprintf(trafficPrefix, mysqlGreetingTrace, addr.String())
                    syscall.Write(fd, []byte(prefix))
                }
            }
        }()
        return err
    })
}

3.2.4 关键模块四：流量匹配（Chunk 评分算法）

📁 replayer-agent/logic/match/match.go 🏷️ 相似度评分 + 游标优化

要解决的问题：回放时，业务服务向 Mock Server 发来一条出站请求，Mock Server 需要从录制 Session 的多个 CallOutbound 中找到最匹配的一条返回响应。 这个问题的难点在于：请求内容可能因时间戳、traceID、序列号等字段而与录制时不完全相同；多个下游类型（MySQL/Redis/HTTP）的请求格式差异巨大； 并发回放时同一 Session 的多条 outbound 请求可能乱序到达。

算法核心：将请求切分为固定 16 字节的 chunk，逐 chunk 在所有候选 CallOutbound 的请求体中查找匹配， 累计命中 chunk 数作为得分，最终选择得分最高的候选。第一个 chunk 在起始位置命中时权重加倍（scores[j] += len(chunks)）， 以优先匹配协议头完全一致的请求。匹配阈值采用 mark（得分/总chunk数）控制：首次匹配 mark > 0.1， 后续匹配 mark > 0.85，减少误匹配。

游标优化：MaxMatchedIndex 游标记录当前已匹配到的最大 Action 下标， 防止并发回放时"颠倒顺序"问题——假设 session 中有两个相同的 MySQL 查询，游标保证第二次匹配一定选择下标更大的那一条。

// 文件: replayer-agent/logic/match/match.go (line 52-136)
// DoMatchOutboundTalk 核心匹配算法
func (m *Matcher) DoMatchOutboundTalk(
    ctx context.Context, session *replaying.Session, lastMatchedIndex int,
    request []byte, chunks [][]byte) (int, float64, *recording.CallOutbound) {

    reqCandidates := getRequests(session) // 取所有录制 CallOutbound 的请求（已排序 HTTP 参数）
    scores := make([]int, len(session.CallOutbounds))

    for chunkIndex, chunk := range chunks {
        for j, reqCandidate := range reqCandidates {
            if j <= lastMatchedIndex { continue } // 游标过滤，避免重复匹配
            pos := bytes.Index(reqCandidate, chunk)
            if pos >= 0 {
                if chunkIndex == 0 && pos == 0 && lastMatchedIndex == -1 {
                    scores[j] += len(chunks) // 首个 chunk 在起始位置命中，权重加倍
                } else {
                    scores[j]++
                }
            }
        }
    }

    // 计算 mark（匹配度）并与阈值比较
    mark := float64(maxScore) / float64(len(chunks))
    if lastMatchedIndex != -1 && mark < 0.85 { return -1, 0, nil } // 非首次要求高精度
    if lastMatchedIndex == -1 && mark < 0.1  { return -1, 0, nil }

    m.Visited[maxScoreIndex] = true                    // 标记已匹配，降低重复匹配权重
    return maxScoreIndex, mark, session.CallOutbounds[maxScoreIndex]
}

3.2.5 关键模块五：时间重置（Mock time.Now()）

📁 replayer/fastmock/time.go 🏷️ Monkey Patching + Goroutine-Local State

要解决的问题：许多业务逻辑依赖当前时间（如 Token 有效期验证、签名生成、限流窗口计算）。 如果回放时返回真实的当前时间，这些逻辑可能因为"时间过期"而产生与录制时不同的行为，导致回放误报。

解决方案：利用与 syscall.Connect 相同的 Monkey Patching 机制，将全局 time.Now() 替换为一个函数： 该函数根据当前 goroutine ID 在 ReplayerGlobalThreads 中查找回放时间戳（由入站请求的 Sharingan-Replayer-Time header 携带）， 如果找到则返回录制时的时间，否则返回真实时间。这样每个回放请求都"活在"它被录制时的那个时间点。 

// 文件: replayer/fastmock/time.go (line 12-33)
// MockTime 将 time.Now() 替换为返回录制时的时间戳
func mockTimeNow() {
    monkey.MockGlobalFunc(time.Now, func() time.Time {
        threadID := internal.GetCurrentGoRoutineID()
        replayTime := int64(0)

        // 从当前 goroutine 的 Thread 中取录制时的时间戳
        if thread := ReplayerGlobalThreads.Get(threadID); thread != nil {
            replayTime = thread.replayTime
        }

        // 非回放 goroutine（如 agent 自身的定时任务）返回真实时间
        if replayTime == 0 {
            return internal.TimeNow()
        }

        // 将纳秒时间戳转换为 time.Time，还原录制时刻
        sec  := replayTime / 1000000000
        nsec := replayTime % 1000000000
        return time.Unix(sec, nsec)
    })
}

4 方案评价

4.1 优势分析

  • 零业务代码入侵：所有 Hook 通过 build tag 切换，业务代码不感知录制/回放逻辑的存在。
  • 下游依赖完全隔离：回放时 MySQL、Redis、HTTP、Thrift 等所有下游均被 Mock，测试环境无需搭建完整依赖链。
  • 时间一致性：time.Now() 被重置为录制时刻，消除了时间相关逻辑的干扰，大幅降低回放误报率。
  • 协议无关：Chunk 评分算法基于字节相似度，无需了解协议细节即可匹配 MySQL、Redis、HTTP 等不同格式的请求。
  • 高并发支持：goroutine-local Session 机制无锁高效，Parallel 回放默认并发度 10，支持快速批量回归。
  • 噪音管理：支持通过 API 标记噪音（如 traceID、时间戳字段），diff 时自动忽略已知的非功能性差异。

4.2 局限分析

  • 强依赖定制 Go 版本：录制侧需使用经过修改的 Go 编译器（go1.10~go1.15），无法直接升级到官方新版本，长期维护成本高。
  • Monkey Patching 脆弱性：gomonkey 依赖修改内存机器码，需关闭内联（-gcflags="all=-N -l"），在不同 CPU 架构（如 ARM）上兼容性存疑，且与 Go race detector 不兼容。
  • 写流量安全隔离依赖手工配置：虽然文档声明支持写流量回放不污染数据，但具体隔离逻辑需要业务方自行配置数据库白名单，存在误操作风险。
  • 仅支持 Go 服务：录制侧深度依赖 Go 运行时 Hook，无法直接用于 Java/Python 等其他语言服务。
  • Session 存储耦合：默认存储为本地文件，生产级使用需对接 ES 或其他存储，运维复杂度增加。
  • 项目已归档：仓库于 2026 年 4 月被归档（archived），不再维护，生产使用需自行 fork 维护。
