browser-harness 深度解读

极简裸 CDP 自愈式浏览器控制框架（~1000 行，同 browser-use 生态）
browser-harness 是 browser-use 团队推出的第二个开源项目，代码仅 ~1000 行，理念却截然不同： 它用一根 WebSocket 直连用户正在运行的 Chrome，把所有决策权交给 LLM（Claude Code、Codex 等编码 Agent）， 让 Agent 在遇到缺失能力时直接写代码扩展工具集，并将踩坑经验沉淀为"Domain Skills"知识库，每次运行都比上次更聪明。 读完本文，你将理解"自愈式 Harness"的核心思想，以及为什么在某些场景下"裸金属"比高级框架更有效。

核心结论

  • 整个框架是 4 个核心文件约 1000 行：daemon.py（CDP 代理）、helpers.py（浏览器原语）、_ipc.py（Unix/TCP 传输）、run.py（CLI 入口）。没有框架层、管理层或事件总线。
  • Daemon 是唯一持久进程，持有与 Chrome 的单条 CDP WebSocket，所有 browser-harness <<'PY'...PY 调用通过 Unix socket（POSIX）或 TCP loopback（Windows）向它发 JSON 请求，它转发给 Chrome 并返回结果。
  • 截图优先 + 坐标点击：Agent 的标准工作流是 capture_screenshot() → 读像素坐标 → click_at_xy(x, y)。Input.dispatchMouseEvent 在合成器层处理，自动穿透 iframe、shadow DOM、跨域框架，无需特殊处理。
  • 自愈机制：agent_helpers.py 初始为空文件，由 Agent 在执行任务时按需写入新的辅助函数；这些函数会被 helpers.py 在运行时动态 importlib.exec_module 加载，持久化到下次调用。
  • Domain Skills：100+ 个站点的 Markdown 知识文件（选择器、API 路径、踩坑记录）由 Agent 在实际任务中生成；goto_url() 在 BH_DOMAIN_SKILLS=1 时自动返回对应域名的 skill 文件列表，让 Agent 先查手册再行动。

1 摘要

1.1 项目背景

browser-use 是一个高度抽象的 AI 浏览器框架，提供 DOM 索引、循环检测、消息压缩等复杂特性。 但在实际使用中，团队发现：对于编码 Agent（Claude Code、Cursor、Codex）来说， 这些高层抽象反而是阻碍——Agent 自身的推理能力已经足够强大， 它只需要一个"透明的窗口"看到浏览器，然后自己决定怎么操作。

2025 年，browser-use 团队发布了 browser-harness：一个"让 LLM 直接操作 Chrome"的极简脚手架。 它的设计哲学源自 The Bitter Lesson of Agent Harnesses（苦涩的框架教训）： 框架越薄越好，把能力交给 Agent，而不是用框架的逻辑替代 Agent 的判断。 上线数月已获得 13.9k Star，贡献了 100+ 个站点的 Domain Skills。

1.2 项目预期

1.2.1 预期一：裸 CDP 直连（零中间层）

Agent 通过 browser-harness <<'PY'...PY 执行任意 Python 代码， 代码中可以调用预导入的辅助函数（goto_url、js、cdp 等）， 也可以直接调用 cdp("Domain.method", **params) 执行任意原始 CDP 命令。 整个调用路径：Agent Python 代码 → Unix Socket → Daemon → Chrome DevTools WebSocket → 返回， 没有任何抽象层"帮你做决定"。

1.2.2 预期二：自愈式扩展（Agent 编写工具）

当 Agent 遇到框架未提供的能力（如特殊文件上传、拖拽、Shadow DOM 访问）， 它可以直接在 agent-workspace/agent_helpers.py 中写入新的辅助函数。 下次调用时，helpers.py 会自动 importlib.exec_module 这个文件， 新函数立即可用，无需重启 Daemon，无需修改任何核心代码。 "Harness improves itself every run"——工具集随使用自动增长。

1.2.3 预期三：Domain Skills 知识沉淀

Agent 在完成任务时发现的非显而易见信息（稳定的 CSS 选择器、私有 API 端点、站点特有的等待时机）， 会被写入 agent-workspace/domain-skills/<站点>/ 目录的 Markdown 文件。 goto_url(url) 在 BH_DOMAIN_SKILLS=1 时会在返回值中附上对应域名的 skill 文件列表， 让 Agent 在开始任务前先读"前辈踩坑记录"，避免重复探索已知问题。 这套机制实现了跨任务、跨用户的知识共享（通过 GitHub PR 贡献）。

2 项目设计理念

2.1 极简主义：没有管理层

SKILL.md 中明确写道："Don't add a manager layer. No retries framework, session manager, daemon supervisor, config system, or logging framework." 这不是技术上做不到，而是刻意的设计决策。 每增加一层抽象，就会在 Agent 和浏览器之间增加一个"替你做决定"的节点， 限制了 Agent 的自由度。browser-harness 只提供"原材料"，决策全部交给 Agent。

整个框架的代码量（~1000 行）约等于 browser-use 单一文件（agent/service.py ~4000 行）的四分之一。 Daemon 的错误处理只有一处：检测到 CDP 会话失效时，自动重新 attach_first_page()， 其余一律透传给调用者。

2.2 截图优先：坐标点击而非 DOM 索引

browser-use 通过构建"DOM 索引化视图"让 LLM 知道哪些元素可以点击； browser-harness 的策略则是：截图 → 读像素坐标 → 直接点击。 Input.dispatchMouseEvent 在 Chrome 的合成器层（compositor）处理， 自然穿透 iframe、shadow DOM、跨域框架，无需任何特殊处理。

这个选择源于一个实用主义观察：坐标点击对 iframe 重度网站（Azure、Salesforce、Shopify Admin） 的支持远比 DOM 遍历稳定，因为这些网站的 DOM 结构复杂且不稳定。 SKILL.md 明确说："Drop to DOM only when the target has no visible geometry (hidden input, 0×0 node)."

2.3 Agent 即开发者

browser-harness 把 Agent 当作开发者而非用户来对待。 它不试图帮 Agent 解析网页、不做循环检测、不做消息压缩—— 这些都是 Agent 自己该做的事。 框架只负责"让 Agent 的代码能跑起来"：确保 Daemon 运行，确保 CDP 连接活跃，提供基础原语。 当 Agent 需要更高级的能力时，它写代码来实现，而不是等框架更新。

2.4 Daemon 单点持久连接

CDP WebSocket 连接建立需要时间，且 Chrome 对每个 target 的并发 session 数有限制。 browser-harness 的 Daemon 持有一条持久的浏览器级 WebSocket， 每次 browser-harness <<'PY'...PY 调用都通过 Unix socket 复用这条连接， 而不是重新建立 WebSocket。 这使得频繁的短任务（如"截图看下当前状态"）几乎没有启动开销。

3 系统详细设计

3.1 系统架构设计

browser-harness 由三层构成：Agent 执行层（run.py + helpers）、Daemon IPC 层（_ipc.py + daemon.py）、浏览器层（Chrome CDP）。 Agent 每次调用本质上是向 Daemon 发送一条 JSON 消息，Daemon 透传给 Chrome，返回结果。

单次调用的完整路径： (1) Agent 通过 shell heredoc 执行 browser-harness <<'PY'...PY； (2) run.py 调用 ensure_daemon()（若未运行则以 subprocess.Popen 后台启动 Daemon）； (3) exec(code, globals()) 执行 Agent 的 Python 代码，其中所有辅助函数已预导入； (4) 每个 goto_url()、cdp() 等调用通过 _ipc.connect() 打开短连接，发送 JSON 请求，读取 JSON 响应，关闭连接； (5) Daemon 的 handle() 方法将请求转发给 Chrome CDP，返回结果。

3.2 关键模块实现细节

3.2.1 关键模块一：Daemon — CDP 代理中枢

📁 src/browser_harness/daemon.py 🏷️ 代理模式 + asyncio 事件循环

核心职责：Daemon 是唯一需要长期运行的进程。它在启动时通过读取 Chrome profile 目录中的 DevToolsActivePort 文件定位 Chrome 的 CDP WebSocket 地址， 建立连接，并附着（attach）到第一个真实标签页。之后作为 IPC 服务器监听来自 helpers 的请求。

事件缓冲：Daemon 对 CDP 事件（Page、Network、DOM 等）维护一个大小为 500 的 deque 缓冲， helpers 通过 drain_events() 批量消费。这使得 wait_for_network_idle() 可以无需 Daemon 修改，纯粹在 helpers 层实现：轮询 drain_events，追踪 in-flight 请求集合， 直到 500ms 内没有新的 Network 事件为止。

会话管理：Daemon 内部维护 self.session（当前 CDP session ID）和 self.target_id。 switch_tab() 会更新 Daemon 的 session（通过 meta: set_session 元命令）， 同时并行地在旧 session 上禁用 Network（减少后台 tab 的噪音），在新 session 上启用四个 CDP domain（Page/DOM/Runtime/Network）。

# Daemon.handle() 是所有 IPC 请求的统一入口
async def handle(self, req):
    meta = req.get("meta")

    # "元命令"处理：这些是框架内部逻辑，不需要转发给 Chrome
    if meta == "ping":         return {"pong": True, "pid": os.getpid()}
    if meta == "drain_events": # 返回并清空事件缓冲队列
        out = list(self.events); self.events.clear()
        return {"events": out}
    if meta == "session":      return {"session_id": self.session}
    if meta == "set_session":  # switch_tab() 调用后更新 session
        old_session = self.session
        self.session = req.get("session_id")
        # 并行：在旧 session 禁用 Network（减少后台 tab 噪音），在新 session 启用四个 domain
        tasks = []
        if old_session and old_session != self.session:
            tasks.append(disable_old())
        tasks.append(self._enable_default_domains(self.session))
        await asyncio.gather(*tasks)  # 并行执行，最坏延迟 = 单次 CDP RTT
        return {"session_id": self.session}
    if meta == "pending_dialog": return {"dialog": self.dialog}
    if meta == "shutdown":    self.stop.set(); return {"ok": True}

    # 普通 CDP 方法：透传给 Chrome
    method = req["method"]
    params = req.get("params") or {}
    # Target.* 是浏览器级调用，不能带 session_id；其他调用默认使用当前 session
    sid = None if method.startswith("Target.") else (req.get("session_id") or self.session)
    try:
        return {"result": await self.cdp.send_raw(method, params, session_id=sid)}
    except Exception as e:
        msg = str(e)
        # Session 失效时自动重新附着（唯一的错误恢复逻辑）
        if "Session with given id not found" in msg and sid == self.session:
            if await self.attach_first_page():
                return {"result": await self.cdp.send_raw(method, params, session_id=self.session)}
        return {"error": msg}

3.2.2 关键模块二：IPC 传输层

📁 src/browser_harness/_ipc.py 🏷️ 跨平台 IPC + 安全令牌

双模式传输：POSIX（macOS/Linux）使用 AF_UNIX 域套接字（/tmp/bu-default.sock）， 通过 umask 0o077 + bind() 确保文件权限为 0600，只有当前用户可连接，无需额外认证。 Windows 使用 TCP loopback（127.0.0.1:随机端口），端口号和随机安全 token 写入 .port 文件， 每次请求必须携带 token，防止本机其他进程伪装调用。

防 Stale PID 攻击：ping() 和 identify() 不做裸 TCP 连接检测， 而是发送 {"meta": "ping"} 并验证响应必须是 {"pong": true, "pid": int}。 这防止了 Daemon 崩溃后端口被其他进程复用时的误判。 pid 的验证还特别排除了 bool 类型（Python 中 isinstance(True, int) == True）， 并限制范围在 (0, 2**31) 内，防止 PID 为 0（信号广播）或负数（进程组）。 

# 文件: src/browser_harness/_ipc.py (line 105-123)
# ping() 防止 stale port 文件导致的误判
def ping(name, timeout=1.0):
    try:
        c, token = connect(name, timeout=timeout)
    except (FileNotFoundError, ConnectionRefusedError, ...):
        return False
    try:
        resp = request(c, token, {"meta": "ping"})
        # 严格验证：必须是 dict 且 pong 字段为 True
        # isinstance 不够安全（True 是 int 的子类），用 resp.get() 保守判断
        return isinstance(resp, dict) and resp.get("pong") is True
    except ...: return False
    finally:
        try: c.close()
        except OSError: pass

3.2.3 关键模块三：agent_helpers.py — 自愈扩展机制

📁 agent-workspace/agent_helpers.py（Agent 可编辑） 🏷️ 运行时动态加载 + 开放扩展

核心机制：helpers.py 末尾调用 _load_agent_helpers()， 通过 importlib.util.spec_from_file_location 动态加载 agent_helpers.py， 并将其所有公共符号（不以 _ 开头）注入到 helpers.py 的 globals() 中。 这意味着 Agent 写入 agent_helpers.py 的任何函数，下次 browser-harness <<'PY' 调用时都自动可用，就像内置函数一样。

自愈场景示例：Agent 需要上传文件，但 upload_file() 内置函数需要 CSS selector， 而某个网站的文件输入框藏在 shadow DOM 中。Agent 在 agent_helpers.py 中写入 upload_via_shadow_dom(host_selector, file_path)，下次任务就可以直接调用。 这个过程完全由 Agent 自主完成，无需 PR 或等待框架更新。

# 文件: src/browser_harness/helpers.py (line 488-503)
# _load_agent_helpers: 动态加载 Agent 写的辅助函数
def _load_agent_helpers():
    p = AGENT_WORKSPACE / "agent_helpers.py"
    if not p.exists(): return

    spec = importlib.util.spec_from_file_location("browser_harness_agent_helpers", p)
    if not spec or not spec.loader: return

    module = importlib.util.module_from_spec(spec)
    spec.loader.exec_module(module)

    # 将所有公共符号（不以 _ 开头）注入到 helpers.py 的全局命名空间
    # 这样 Agent 在 browser-harness <<'PY' 中直接调用自定义函数
    for name, value in vars(module).items():
        if name.startswith("_"): continue
        globals()[name] = value  # 覆盖同名核心函数是允许的（Agent 可以 monkey-patch）

3.2.4 关键模块四：Domain Skills — 集体知识积累

📁 agent-workspace/domain-skills/（Agent 可编辑，社区共建） 🏷️ 知识库模式 + 域名路由

机制：每个站点对应一个目录（如 domain-skills/github/）， 目录下有多个 Markdown 文件，每个文件针对该站点的一种操作模式（scraping、checkout、navigation 等）。 文件内容是经过实际测试的代码片段和踩坑说明，由 Agent 在任务执行中生成，而非手写。

激活方式：goto_url(url) 在 BH_DOMAIN_SKILLS=1 时， 会解析 URL hostname，在 domain-skills/ 中查找对应目录， 将最多 10 个 skill 文件名附加到返回值中（{"url": ..., "domain_skills": ["scraping.md", ...]}）。 Agent 看到这个信号后，应先读取对应文件，再决定操作策略。

写入规范：SKILL.md 明确要求 Agent 记录"地图"而非"日记"—— 不写像素坐标（会随布局变化），不写任务叙述，不写密钥； 只记录持久有效的信息：稳定的 CSS 选择器、API 端点、框架特有的等待时机、边界条件。 目前已有 GitHub、Amazon、LinkedIn、Reddit、Shopify Admin 等 100+ 站点的 skills。 

# 文件: src/browser_harness/helpers.py (line 159-164)
# goto_url 在 BH_DOMAIN_SKILLS=1 时自动附加对应站点的 skill 文件列表
def goto_url(url):
    r = cdp("Page.navigate", url=url)
    if os.environ.get("BH_DOMAIN_SKILLS") != "1":
        return r
    # 解析 hostname，匹配 domain-skills/ 目录（去 www. 前缀，取第一段）
    d = AGENT_WORKSPACE / "domain-skills" / (
        urlparse(url).hostname or ""
    ).removeprefix("www.").split(".")[0]
    # 返回最多 10 个 .md 文件名
    return {**r, "domain_skills": sorted(p.name for p in d.rglob("*.md"))[:10]} if d.is_dir() else r

3.3 与 browser-use 的设计对比

两个项目来自同一团队，却代表了截然不同的设计哲学：

browser-use（高层框架）

  • 用户：Python 开发者，通过 Agent(task=...) API 使用
  • DOM 感知：AX Tree + DOMSnapshot 融合，为每个元素分配 [n] 索引
  • 决策层：LLM 通过结构化 JSON 输出决定动作
  • 循环检测：ActionLoopDetector + PageFingerprint
  • 上下文管理：MessageCompaction 自动压缩历史
  • 规模：~15000 行代码，12+ 个 Watchdog 模块
  • 代价：每步 DOM 序列化开销，上下文 Token 消耗高

browser-harness（裸金属脚手架）

  • 用户：编码 Agent（Claude Code、Cursor），通过 shell heredoc 使用
  • DOM 感知：截图 → 坐标点击；需要时用 js() 读 DOM
  • 决策层：Agent 自身的推理，写 Python 代码实现逻辑
  • 循环检测：无（Agent 自行判断）
  • 上下文管理：无（Agent 自行管理）
  • 规模：~1000 行代码，4 个核心文件
  • 代价：对 Agent 的推理能力要求更高

两者并非竞争关系：browser-use 适合"给一个任务描述，框架帮你完成"的场景； browser-harness 适合"编码 Agent 需要完整控制权"的场景。 团队将两者都维护，也提供同一套 Cloud 基础设施（Browser Use Cloud）支持两者的远程浏览器需求。

4 方案评价

4.1 优势分析

  • 极低学习曲线：整个框架可以在 30 分钟内读完理解，没有隐藏的行为。Agent 看到的是 Python + CDP，没有框架魔法。
  • 完全透明：所有 CDP 调用都可见、可审计、可调试。cdp("Domain.method", **params) 让 Agent 可以使用任何 CDP 能力，不受框架功能集限制。
  • iframe/shadow DOM 零阻力：坐标点击在合成器层处理，自然穿透各类复杂 DOM 结构，是 Shopify Admin、Salesforce 等 iframe 重度网站的最优解。
  • 自愈积累：agent_helpers.py 和 domain-skills 随使用自动增长，每次任务结束后工具集和知识库都比之前更强。
  • 超低开销：Daemon 持久持有 CDP 连接，单次调用只有 Unix socket 往返开销，截图和页面操作几乎是直接 CDP 的延迟。
  • 云浏览器支持：一行代码 start_remote_daemon("work") 即可接入 Browser Use Cloud，获得 stealth 浏览器、代理、CAPTCHA 解决能力，且 Daemon 模型完全一致。

4.2 局限分析

  • 依赖 Agent 的编程能力：框架几乎不做任何"智能化"处理，需要 Agent（Claude Code 等）具备足够强的代码生成和错误恢复能力，对弱小 LLM 效果差。
  • 无内置重试/恢复机制：Daemon 只有一处错误恢复（session 失效时重新 attach），其他错误直接抛出给 Agent 处理，Agent 需要自行实现重试逻辑。
  • 截图定位依赖视觉能力：坐标点击模式要求 LLM 能从截图中准确读取像素坐标，对视觉模型的精度有要求；布局变化（响应式设计、弹窗遮挡）会导致坐标失效。
  • Domain Skills 质量参差：社区贡献的 skills 质量和时效性无法保证，过时的 CSS selector 可能导致 Agent 信任错误信息、走弯路。
  • Windows 支持相对脆弱：TCP loopback + 随机端口方案在 Windows 下有端口冲突和文件写入竞争的边缘问题，AF_UNIX 路径更稳定（项目中有多处 IS_WINDOWS 分支处理）。
  • 无并发安全：Daemon 的 self.session 是单个值，多个并发 Agent 实例通过同一 BU_NAME 会互相覆盖 session，并发场景需要使用不同 BU_NAME 隔离。
