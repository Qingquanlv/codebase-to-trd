BMad TEA 深度解读

Test Engineering Architect — AI 原生测试方法论框架
BMad TEA（Test Engineering Architect）是 BMad Method 生态的专项测试模块，它提供了一位 AI 测试架构师「Murat」和 9 条结构化工作流，通过将结构化 Markdown 指令注入 LLM 上下文窗口，使 LLM 本身成为执行引擎——无需任何外部运行时，就能输出风险驱动的测试计划、自动化脚本和发布质量门决策。

核心结论

  • 「LLM 即引擎」是其最大设计创新：工作流是结构化 Markdown，LLM 逐步文件执行，无外部调度器，可运行于任何指令遵循能力足够的模型。
  • 三大机制协同降低上下文消耗：按需步骤加载（JIT）、分级知识索引（core / extended / specialized）、子 Agent 隔离并行——综合节省上下文 40–50%。
  • 置信门控（Confidence Gate）是防止 LLM 幻觉的核心安全机制，要求在生成任何非平凡测试产出前，先提供带证据的置信度评分，低于阈值则强制停止并向用户提问。

1 摘要

1.1 项目背景

AI 编码工具（Claude Code、GitHub Copilot、Cursor、Codex 等）在生成业务代码方面已相当成熟，但在测试工程领域却长期缺乏系统化方法论支撑。开发团队面临的痛点包括：

  • AI 生成的测试代码往往「看起来正确但测不到真实逻辑」——选择器拼造、接口路径凭空捏造、风险评估凭直觉；
  • 测试覆盖率缺乏可量化的风险基线，无法支撑「是否可以发布」的质量门决策；
  • 单次 Prompt 无法处理跨越多步骤、多文件的复杂测试工程任务（框架搭建、ATDD 红阶段、全量覆盖扩展）；
  • 不同 AI 工具（Claude、Codex、Cursor、Windsurf）各自为政，无法共享统一的测试最佳实践库。

BMad Method 是 bmad-code 组织构建的「结构化 AI 工作流」生态，其核心思想是：将大型模糊任务拆解为有明确交接点的小步骤，再配以共享知识库，使 AI 输出具有可重复性。TEA（Test Engineering Architect）是 BMad Method 的专项测试模块，于 2025 年末正式发布，到 2026 年 5 月已迭代至 v1.19.0，积累了 47 个版本发布。

1.2 项目预期

1.2.1 预期一：AI 原生测试工程师

TEA 的目标不是「生成测试代码的工具」，而是为每个项目配备一位具有明确身份和原则的 AI 测试架构师「Murat」。Murat 能够主导风险评估、制定测试策略、选择测试框架、评审现有测试质量，并在发布前做出量化的 go / no-go 决策——覆盖测试工程师从需求阶段到 CI/CD 上线的完整职责链。

1.2.2 预期二：可衡量的质量门控

传统的「是否可以发布」决策依赖主观经验和团队共识。TEA 通过风险矩阵（概率 × 影响 = P0–P3 优先级）、需求到测试的可追溯性矩阵（Trace 工作流）、NFR 证据审计（NFR 工作流）三个维度，将发布决策转化为可量化、可审计的数据——满足 FDA、SOC2、ISO 等合规要求。

1.2.3 预期三：跨平台多框架覆盖

TEA 设计之初就面向多样化的技术栈和 AI 工具生态。在测试框架侧支持 Playwright、Cypress、Jest、Vitest、pytest、JUnit、Go test、dotnet test、RSpec；在 AI 工具侧通过安装器生成针对 10+ 平台的启动产物（Claude Code 的 .claude/commands/、Codex 的 .agents/skills/、Cursor 的 .cursor/rules/ 等），一套工作流定义多端复用。

2 项目设计理念

2.1 LLM 即引擎（No External Runtime）

BMad 最根本的设计决策是：不引入任何外部调度器或运行时。整个工作流完全由结构化 Markdown 文件驱动，LLM 本身就是执行引擎。每个步骤文件在末尾明确指向下一个步骤文件的路径（{skill-root}/steps-c/step-02-identify-targets.md），LLM 读取、执行、保存输出，然后自行加载下一文件——这使得 TEA 能在任何具备足够指令遵循能力的 LLM 上运行，不依赖任何特定平台的 API。

与之形成对比的是传统 AI Agent 框架（LangChain、AutoGPT）的做法：由 Python/JS 代码编排 LLM 调用序列，工作流逻辑存在于宿主程序中。BMad 则将逻辑完全内化到 LLM 上下文，消除了对特定语言运行时的依赖。

2.2 按需加载上下文（Just-in-Time Loading）

LLM 上下文窗口是稀缺资源。TEA 通过三层机制最小化上下文占用：

  1. 步骤 JIT 加载：任何时刻上下文中只有当前步骤文件；未来步骤从不预加载。每个步骤执行完毕才加载下一个，历史步骤内容不在窗口中保留。
  2. 分级知识注入：50+ 知识碎片按 core（始终加载）/ extended（按需）/ specialized（仅当相关时）三级分类。一个纯后端项目约加载 1,800 行知识内容，全栈项目约 4,500 行，比全量加载节省 40–50%。
  3. 子 Agent 隔离：重量级工作流（如 Automate）将 API 测试生成和 E2E 测试生成分派给独立的子 Agent，各自运行在隔离上下文中，仅将结构化 JSON 结果写入临时文件，父工作流只读取聚合后的结果，不接触子 Agent 的完整历史。

2.3 置信门控防止幻觉（Confidence Gate）

LLM 生成测试代码的核心风险不是「拒绝生成」，而是「生成看起来可信实则虚构的内容」——凭空拼造的 CSS 选择器、不存在的 API 路径、凭感觉给出的风险分数。TEA 通过 Confidence Gate 强制要求：在生成任何非平凡的测试产物之前，先输出带证据的置信评分。评分低于 5 时强制停止生成并向用户提问，5–6 时生成但暴露假设，≥7 时方可正常生成。

2.4 风险驱动测试策略（Risk-Based Testing）

测试资源永远有限，不可能覆盖所有场景。TEA 以「概率 × 影响」风险矩阵为核心，将测试场景分为 P0（必须测试）到 P3（时间允许时测试）四个优先级，使团队始终聚焦于最高价值的测试。每个风险项需要明确的所有者、缓解计划和截止日期——这既是工程纪律，也是合规审计的证据链。

2.5 可组合式定制层（Layered Customization）

TEA 采用「三层覆盖」模型处理团队差异：customize.toml（基础默认值）→ _bmad/custom/{skill-name}.toml（团队覆盖）→ _bmad/custom/{skill-name}.user.toml（个人覆盖）。标量值直接替换，表格深度合并，数组按 code/id 键追加或替换。这使同一套 TEA 工作流可以在不同项目、不同团队角色之间共享，同时保留各自的定制化空间，且不需要修改核心文件。

3 系统详细设计

3.1 系统架构设计

TEA 由四个层次组成：用户通过 AI 工具触发 Agent 人格层，人格层根据用户意图分派到具体工作流的入口 SKILL.md，工作流入口按三态（Create/Edit/Validate）路由到步骤文件链，步骤文件按需从知识库读取知识碎片、填充模板，最终写出测试产物（测试计划、测试代码、可追溯性矩阵、质量门报告）。

整体数据流的关键特征是单向性和步骤原子性：每个步骤文件是一个独立的执行单元，读取前序步骤写出的 YAML frontmatter 进行恢复，执行后追加结果到输出文件。Validate 模式是整个工作流的质量反馈环，可以随时对已有产物进行独立的评估，无需重新执行 Create 链。

3.2 关键模块实现细节

3.2.1 关键模块一：Agent 人格层（Murat Persona）

📁 src/agents/bmad-tea/SKILL.md 🏷️ Persona Injection Pattern 🏷️ Menu Dispatch

Agent 人格层是整个 TEA 的「门面」，它完成三件事：将 Murat 的身份、原则和能力表注入 LLM 上下文；解析定制化配置（customize.toml 三层覆盖）；根据用户初始意图直接分派或展示菜单。

激活序列设计为 8 步，顺序严格：①解析定制块（运行 Python 解析器或手工合并三层 TOML）→②执行前置步骤 → ③注入人格 → ④加载持久事实 → ⑤加载项目配置 → ⑥向用户打招呼 → ⑦执行后置步骤 → ⑧分派菜单或直接执行意图。其中「持久事实」可以是任意字符串，也可以是以 file: 前缀指向的文件路径——这允许团队将项目约定、API 规范等注入为 Murat 的长期记忆。

3.2.2 关键模块二：工作流三态架构（Tri-Modal Workflow）

📁 src/workflows/testarch/*/SKILL.md + steps-c/ + steps-e/ + steps-v/ 🏷️ State Machine Pattern 🏷️ YAML Frontmatter Progress

每条工作流包含三条独立的步骤链，对应三种执行模式：Create 模式（steps-c/，5-9 个顺序文件，新建产出）、Edit 模式（steps-e/，固定 2 个文件：评估目标 + 应用修改）、Validate 模式（steps-v/，固定 1 个文件：对照 checklist 评估）。三态之间相互独立，但 Edit 和 Validate 依赖 Create 的输出文件。

恢复（Resume）机制通过 YAML frontmatter 实现：每个步骤在执行后向输出文件追加 stepsCompleted、lastStep、lastSaved 字段。Resume 时，步骤 01b 读取这些字段，直接路由到下一个未完成步骤，无需重跑已完成步骤。这使得即使 LLM 上下文被中断（超时、切换会话），工作流也能从断点续跑。

以旗舰工作流 Automate（测试自动化扩展）为例，其 Create 链包含 9 个步骤文件：

3.2.3 关键模块三：分层知识库（Tiered Knowledge Base）

📁 src/agents/bmad-tea/resources/tea-index.csv 📁 src/agents/bmad-tea/resources/knowledge/*.md 🏷️ Tiered Index Pattern

知识库是 TEA 输出质量的核心基础设施。它由一个 CSV 索引文件（tea-index.csv）和 50+ 个 Markdown 知识碎片组成，覆盖从夹具架构到 Pact 合同测试、从 Webhook 测试到 CI 燃尽策略的全域测试工程知识。

知识碎片按三个层级分类，驱动选择性加载：

  • core（核心）：20 个碎片，始终加载。包含夹具架构、网络优先安全守卫、数据工厂、风险治理、P0-P3 优先级矩阵、置信门控等基础知识。
  • extended（扩展）：18 个碎片，按需加载。包含 Playwright 配置守护、时序调试、CI 燃尽策略、NFR 评审标准等进阶知识。
  • specialized（专项）：12 个碎片，仅当特定配置标志或检测到相关技术栈时加载。包含 Pact 合同测试全套（pactjs-utils-overview / zod-to-pact / consumer-helpers / provider-verifier / request-filter / pact-consumer-framework-setup）、Pact Broker Webhooks、邮件认证测试等。

每个碎片在 CSV 中有 id, name, description, tags, tier, fragment_file 六列。步骤文件在执行前读取 CSV，根据当前任务的标签（如 api, backend, contract-testing）和配置标志（tea_use_pactjs_utils: true）筛选并加载相关碎片。这实现了「只将当前任务需要的知识注入上下文」的精准控制。

值得注意的是，每条工作流的 resources/ 目录都刻意复制了所需的 TEA 知识子集，而不是在运行时跨技能边界引用中央路径。这确保每条工作流可以被独立安装、复制或调用，不依赖其他技能的文件系统位置。

3.2.4 关键模块四：Automate 旗舰工作流（子 Agent 并行编排）

📁 src/workflows/testarch/bmad-testarch-automate/steps-c/ 🏷️ Adaptive Orchestration 🏷️ Subagent Isolation

Automate 是 TEA 最重量级的工作流，也是其并行架构最典型的展示。其设计解决了一个核心矛盾：生成全量 API + E2E 测试需要大量推理，但单次 LLM 上下文无法容纳所有中间状态。

解决方案是 自适应执行模式（由 tea_execution_mode 配置控制）：

  • agent-team 模式：若运行时支持 Agent 团队/委托（如 Codex 的多 Agent 模式），优先使用，实现真正的并行。
  • subagent 模式：若支持孤立子 Agent（如 Claude Code 的 subagent），API 测试 Agent 和 E2E 测试 Agent 并行运行在各自隔离上下文中，通过 /tmp/tea-automate-*-{timestamp}.json 临时文件传递结构化输出。
  • sequential 模式：降级为顺序执行，确保跨环境兼容性。
  • auto 模式（默认）：在步骤 03 执行前探测运行时能力（tea_capability_probe: true），按优先级选择最佳模式。

关键的上下文隔离设计：父工作流在分派子 Agent 时，只传入一个精简的 subagentContext JSON，包含覆盖计划、已加载的知识碎片列表、配置标志——子 Agent 不需要重新读取整个代码库，只需在给定的约束内完成单一任务（API 测试 / E2E 测试），并将结果以固定 JSON schema 输出到临时文件。聚合步骤（step-03c）读取这些 JSON，生成共享的 fixtures，避免重复代码。

3.2.5 关键模块五：置信门控（Confidence Gate）

📁 src/agents/bmad-tea/resources/knowledge/confidence-gate.md 🏷️ Anti-Hallucination Pattern 🏷️ Evidence-Based Generation

置信门控是 TEA 最具独创性的设计之一，它将「LLM 不应该生成虚假测试代码」这一工程原则编码为一个强制输出格式要求，嵌入到所有非平凡测试产出的生成流程中。

核心机制是：在生成选择器、API 路径、风险评分、数据工厂或 Zod Schema 之前，LLM 必须先输出一个标准化的置信评估块，包含 1-10 分的置信分、支撑该分数的具体证据引用（必须是文件路径、合约文档或实际观察到的模式）、以及未解决的未知项列表。

flowchart LR A["需要生成测试产物"] --> B{"评估置信度\n(1-10)"} B -->|"≥ 7\n有充分证据"| C["正常生成\n✅ 无需干预"] B -->|"5-6\n证据部分"| D["生成但暴露假设\n⚠️ 提醒用户检查"] B -->|"< 5\n证据不足"| E["🛑 停止生成\n提一个具体问题\n解决最关键的未知项"] E --> F["用户提供信息\n证据增强"] F --> B C --> G["产出：真实反映\n代码库现状的测试"] D --> G
图 3-4: Confidence Gate 决策流程

门控适用范围精确划定，避免过度官僚化：

  • ✅ 必须应用：选择器/页面对象（需探索真实应用）、API 端点路径（需读取 OpenAPI 规范）、风险分类（需引用概率-影响证据）、Fixture 组合（需理解现有 mergeTests 模式）、Schema 生成（需有合约来源）、数据工厂（需理解生产数据约束）。
  • ❌ 不应用：机械性重构（重命名变量、添加标签）、读取和汇总现有产物、从已收集数据生成报告、完全复制现有模式的简单测试补充。

3.2.6 关键模块六：定制化覆盖系统（Layered Customization）

📁 src/agents/bmad-tea/customize.toml 📁 _bmad/custom/{skill-name}.toml (团队) 📁 _bmad/custom/{skill-name}.user.toml (个人) 🏷️ Three-Layer Override Pattern

定制化系统允许在不修改 TEA 核心文件的前提下，通过 TOML 文件叠加覆盖 Agent 行为和工作流参数。系统在每次激活时由 Python 脚本 _bmad/scripts/resolve_customization.py 计算最终配置，脚本不可用时 LLM 手动应用相同的合并规则。

合并规则：标量值直接覆盖（后者赢）；TOML 表（[table]）深度合并（只覆盖有值的键）；带 code 或 id 键的表数组，匹配则替换对应条目，不匹配则追加；其他数组直接追加。这套规则使团队可以在不复制整个 customize.toml 的情况下，仅覆盖需要变更的菜单项或参数。

典型使用场景：团队 customize.toml 中禁用 Pact 相关菜单项（若项目不使用合同测试）；个人 .user.toml 中调整 Murat 的沟通语言为中文；CI 环境注入固定的配置标志（tea_execution_mode: sequential）以确保确定性执行。 

# _bmad/custom/bmad-tea.toml (团队覆盖示例)
[agent]
communication_style = "concise, bullet-point preferred"  # 覆盖默认风格

# 禁用 Pact 合同测试菜单项（本团队不使用）
[[agent.menu]]
code = "CT"
label = "Contract Testing"
disabled = true  # 追加 disabled 字段到匹配项

# _bmad/custom/bmad-tea.user.toml (个人覆盖示例)
[agent]
role = "senior QA engineer with focus on performance testing"
communication_language = "Chinese"

4 方案评价

4.1 优势分析

  • 零运行时依赖：无需 Python/JS 编排引擎，在任何支持指令遵循的 LLM 上开箱即用，迁移成本极低。
  • 上下文工程领先：JIT 步骤加载 + 分级知识注入 + 子 Agent 隔离三重机制，显著延长有效工作深度，一次会话可完成原本需要多轮的复杂任务。
  • 防幻觉机制内建：Confidence Gate 将 AI 安全原则编码为强制输出格式，不依赖模型自律，可靠性更强。
  • 全覆盖测试生命周期：9 条工作流覆盖从 ATDD 红阶段、框架搭建、CI 配置到可追溯性矩阵和发布门决策的完整链路。
  • 10+ 平台一次安装：Claude Code、Cursor、Codex、GitHub Copilot、Windsurf、Cline 等平台通过统一安装器生成各自的启动产物，维护成本集中在核心工作流定义。
  • 丰富的专项知识库：Pact V4 FFI 安全规则、Webhook 异步测试模式、Playwright-utils 全套工具等稀缺知识已系统化沉淀，避免团队重复踩坑。
  • 渐进式配置设计：大多数变量提供合理默认值（auto 检测栈类型、CI 平台），新团队可零配置上手，按需深化。

4.2 局限分析

  • 不执行测试，只生成代码：TEA 是测试代码生成器而非测试运行器，生成质量依赖 LLM 推理能力，无法自动验证生成的测试是否真正有效。
  • 模型质量强依赖：置信门控等机制假设 LLM 能可靠地遵循结构化指令；弱指令遵循的模型可能跳过步骤或忽略停止规则，导致产出不一致。
  • 知识库维护成本高：每条工作流刻意复制所需知识（自包含原则），当核心知识碎片更新时需同步传播到所有相关工作流的 resources/ 目录，存在维护分散风险。
  • 复杂的配置变量体系：module.yaml 中有 12 个配置变量，部分标注为 FUTURE（尚未激活），新用户难以判断哪些变量当前有实际效果。
  • 子 Agent 特性平台依赖：并行子 Agent 模式依赖特定平台能力（如 Claude Code subagent），auto 模式虽有降级，但降级到 sequential 时性能差异显著。
  • 文件路径系统脆弱性：步骤文件间通过 {skill-root} 变量传递路径，安装位置变化或路径解析错误会导致工作流中断，调试难度较高。
